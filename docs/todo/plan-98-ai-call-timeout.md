# 개발 플랜 — #98 외부 AI 호출 타임아웃

> fix · develop 전체 검토 후속 · #96 위에 스택.

## 1. 이슈 분석

`GeminiReminiscenceCardGenerator`가 기본 요청 팩토리로 `RestClient`를 만든다. 커넥트·리드 타임아웃이 설정돼 있지 않고, 기본값은 무한이다.

호출부가 트랜잭션 안이라는 점이 위험을 키운다.

| 요소 | 값 |
| --- | --- |
| 호출 지점 | `ReminiscenceApplicationService.generateTodayReminiscence` (`@Transactional`) |
| 사진당 재시도 | 최대 3회 |
| 앨범당 사진 | 최대 5장 |
| 트랜잭션 1건당 외부 호출 | **최대 15회** |
| 실행 주기 | 매일 08:00, 전체 앨범 순회(#85) |

업스트림이 응답을 멈추면 스레드가 DB 커넥션을 붙잡은 채 영원히 대기한다. 배치는 진행되지 않고, 다음 날 실행과 겹친다.

### 실패 자체는 이미 안전하다

어댑터가 `catch (Exception ignored)`로 모든 예외를 잡아 안전한 기본 카드로 폴백한다. 타임아웃이 걸려도 카드 생성은 계속된다. **문제는 실패가 아니라 무한 대기다.**

## 2. 설계 판단

### 2-1. 타임아웃으로 상한을 만든다

무한 대기를 유한하게 바꾸는 게 핵심이다. 타임아웃이 걸리면 기존 폴백이 받아 주므로 동작상 달라지는 건 "언젠가 끝난다"는 것뿐이다.

기본값은 커넥트 5초 / 리드 20초로 둔다. 생성형 모델 응답은 수 초가 걸리므로 리드는 넉넉히 잡되, 사람이 기다리는 경로가 아니라 야간 배치라 지나치게 짧게 잡을 이유도 없다.

최악의 경우 앨범당 15 × 20초 = 5분으로 묶인다. 무한과 5분은 성격이 다르다.

### 2-2. 설정으로 뺀다

운영에서 모델이나 네트워크 사정에 따라 조정할 수 있어야 한다. `haemi.ai.gemini.connect-timeout` / `read-timeout`으로 노출한다.

### 2-3. 트랜잭션 분리는 하지 않는다

생성(외부 호출)과 저장(트랜잭션)을 나누는 게 근본 해법이지만, `generateTodayReminiscence`는 앨범 조회·사진 필터·인물 노출 조회·콘텐츠 저장·알림 발송이 한 메서드에 묶여 있어 분리 범위가 크다.

타임아웃만으로 "무한 대기"라는 실제 위험은 사라진다. 구조 개선은 릴리스 이후 별도로 다루는 편이 안전하다.
