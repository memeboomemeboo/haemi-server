# ADR-0001: 인증 계정과 어르신 돌봄 프로필 분리

- 상태: 채택
- 결정일: 2026-08-11
- 관련 명세: 기능명세서 v3.0 F0-01, F0-02, F0-03, F0-04, F0-05

## 배경

기능명세서 v3.0에서 어르신은 단순한 로그인 사용자가 아니다. 어르신은 가족
그룹, 기관 담당자, 기기 및 접근 모드와 관계를 맺고, 생애 정보, 건강 정보,
민감 주제, 인물 노출 정책, 상태 전이의 주체가 된다.

다음 요구사항은 인증 계정의 수명주기와 어르신 돌봄 프로필의 수명주기를
분리해야 한다.

- Mode A는 어르신이 직접 기기를 사용하고, Mode B는 가족 또는 기관 담당자가
  대행할 수 있다.
- 어르신의 입원, 사망, 추모 등 상태는 알림과 콘텐츠 제공을 제어해야 하며,
  로그인 계정이 없거나 탈퇴해도 기록과 정책이 유지되어야 한다.
- 가족과 기관 담당자의 행동은 실제 대상 어르신과 실행자(`operatorId`)를
  구분해 감사할 수 있어야 한다.
- 건강 정보와 생애 정보는 일반 인증 정보보다 강한 접근 제어와 보존 정책이
  필요하다.

`Member(role = ELDER)`를 어르신의 기본 모델로 사용하면, 대행 사용과 상태 보존,
권한 감사, 개인정보 경계를 일관되게 처리하기 어렵다.

## 결정

어르신은 `Member`와 분리된 `Elder` 도메인 엔티티로 모델링한다. 기존 `Member`는
당분간 명칭을 유지하되 인증 계정(`Account`) 경계로 취급한다. 장기적으로는
`Account`로 명칭을 정리할 수 있지만, 이번 결정만으로 기존 테이블이나 API를
일괄 변경하지 않는다.

### 핵심 모델

| 모델 | 책임 |
| --- | --- |
| `Member` (향후 `Account`) | 로그인, 자격 증명, JWT, 계정 정지 및 탈퇴 |
| `Elder` | 어르신 프로필, 접근 모드, 돌봄 상태, 콘텐츠/알림 대상 여부 |
| `FamilyGroup` | 가족 단위 소유 및 협업 경계 |
| `FamilyGroupMember` | `Member`와 `FamilyGroup`의 역할, 관계, 소유자 이양 |
| 기기/접근 연결 | 특정 계정 또는 기기가 특정 `Elder`에 접근하거나 대행할 수 있는 권한 |
| 기관 배정 | 기관 담당자 또는 기관과 `Elder`의 운영 관계 |
| `ElderHealth`, `LifeStory`, `SensitiveTopic` | 어르신에 귀속되는 민감/생애 정보 |
| `Person` | 어르신이 인식하는 인물의 생존 상태와 콘텐츠 노출 정책 |

`Elder`와 `Member`의 직접 연결은 선택적 0..1 : 0..1 관계로 둔다. Mode B로만
운영되는 어르신은 본인 계정이 없어도 된다. Mode A에서 직접 사용하는 어르신은
기기 인증 또는 계정을 연결할 수 있다. 가족 계정, 기관 계정, 어르신 계정 모두
가족/기관 관계 또는 기기 접근 연결을 통해 대상 권한을 판정한다.

`ElderStatus`는 `Elder`가 소유하는 상태 전이 모델이다. 계정의 `ACTIVE`,
`SUSPENDED`, `WITHDRAWN` 같은 인증 상태와 혼용하지 않는다. 콘텐츠 생성, 세션
시작, 사전 다운로드, 알림 발송은 실행 직전에 `ElderStatus`를 다시 확인한다.

## 권한 및 감사 규칙

1. 요청 경로나 본문의 `elderId`만으로 대상 접근을 허용하지 않는다. 인증된
   `Member`가 해당 `Elder`에 대해 유효한 가족/기관 관계 또는 기기 접근 연결을
   갖는지 확인한다.
2. 대행 실행에서는 행위자와 대상자를 분리한다. 이벤트와 변경 이력에는 대상
   `elderId`와 실행자 `operatorId`를 함께 기록한다.
3. 어르신 계정이 탈퇴하거나 기기가 교체되어도 `Elder` 및 돌봄 이력은 독립적으로
   유지한다. 계정 또는 기기 연결만 해제하거나 재발급한다.
4. `Person`의 생존 상태와 노출 상태, `SensitiveTopic`, `ElderStatus`는 콘텐츠
   후보를 선택할 때와 발송 직전에 모두 확인한다.
5. `ElderHealth`는 일반 프로필과 분리하고, 저장 암호화 및 별도 접근 정책을
   적용한다.

## 선택지 검토

### 대안 1: `Member(role = ELDER)`를 어르신의 기본 모델로 사용

채택하지 않는다. Mode B의 무계정 운영, 계정 탈퇴 이후의 상태/추모 기록 보존,
가족 대행의 실행자 감사, 인증 정보와 건강 정보의 분리가 모두 역할 컬럼 하나에
과도하게 결합된다.

### 대안 2: `Elder`를 분리하되 본인 계정 연결을 제공하지 않음

채택하지 않는다. Mode A에서 어르신이 직접 사용하는 기기 또는 계정을 연결할 수
없어 향후 인증 방식 확장과 기기 교체가 불필요하게 제한된다.

## 결과와 구현 영향

이 결정으로 Mode A와 Mode B를 같은 돌봄 대상 모델 위에서 처리하고, 상태 기반
발송 차단과 대행 감사의 기준점을 하나로 만들 수 있다. 기존 API의 단순한 ID
파라미터 수신 방식은 점진적으로 권한 검증으로 교체해야 하며, 조인과 정책 조회가
늘어난다.

마이그레이션은 `Elder` 식별자, 상태, 접근/노출 조회 포트의 계약을 먼저 확정한
뒤 가족 그룹, 어르신, 기기 접근, 건강/생애/민감 정보와 `Person`을 추가한다. 새
API부터 관계 기반 인가와 `operatorId` 기록을 적용하고, 기존 API는 호환 계층을
거쳐 단계적으로 전환한다.

## 후속 결정

- Mode A의 실제 인증 방식: 기기 바인딩과 PIN을 우선 검토한다.
- 건강 정보의 암호화 키 관리 방식과 열람 감사 정책
- 사망 상태의 2단계 확인, 무음 기간, 추모 상태 전이 규칙
- 가족 그룹과 기관 배정의 다대다 허용 범위 및 소유자 이양 규칙
- 어르신, 건강 정보, 이벤트 로그의 동의, 보존, 삭제 정책

## 검증 기준

- 권한이 없는 계정은 임의의 `elderId`를 지정해 프로필, 세션, 알림, 콘텐츠에
  접근할 수 없다.
- 가족/기관의 대행 실행 이벤트에는 `elderId`와 `operatorId`가 모두 남는다.
- 계정이 없는 Mode B 어르신도 프로필, 상태, 가족 관계를 유지할 수 있다.
- 상태 또는 인물 노출 정책상 차단된 어르신에게는 콘텐츠와 알림이 발송되지
  않는다.
